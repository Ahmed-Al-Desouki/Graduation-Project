# Arabic/English Bilingual System Guide

## 1. Executive Summary

The backend now supports a strong bilingual foundation for Arabic and English.

### What the backend supports now

- Persisting each user's preferred language: `en` or `ar`
- Reading and updating that preference through API
- Resolving language from:
  - authenticated user preference
  - query string `?lang=`
  - header `X-App-Language`
  - header `Accept-Language`
- Returning localized API `message` and `error` payloads through a response-localization middleware
- Returning localized model-validation responses
- Returning localized plain-text API responses too
- Returning localized exception messages
- Localizing many backend-generated texts through a central localization service
- Localizing notification titles and notification bodies by recipient language
- Localizing email subjects and email templates by recipient language
- Applying Arabic/English culture rules to backend-generated dates, times, month labels, and formatted amounts
- Supporting unauthenticated localization through `Accept-Language` and `X-App-Language`

### What the backend does not do

- It does not translate user-written free text such as ticket messages, doctor notes, review comments, or patient descriptions
- It does not make the frontend interface bilingual by itself
- It does not remove the need for frontend translation files, locale state, and RTL support

So the backend is now responsible for:

- language preference
- localized backend text
- localized notifications
- localized emails
- culture-aware formatting

The frontend is still responsible for:

- visible UI text
- layout direction
- font selection
- screen-level localization behavior

## 2.2 Language settings API

### Get current language

```http
GET /api/settings/language
Authorization: Bearer <token>
```

Example response:

```json
{
  "language": "ar",
  "isRightToLeft": true,
  "supportedLanguages": ["en", "ar"]
}
```

### Update current language

```http
PUT /api/settings/language
Authorization: Bearer <token>
Content-Type: application/json

{
  "language": "en"
}
```

Example response:

```json
{
  "message": "Language preference updated successfully.",
  "data": {
    "language": "en",
    "isRightToLeft": false,
    "supportedLanguages": ["en", "ar"]
  }
}
```

If the active request language is Arabic, the backend can return the success message in Arabic.

---

## 2.3 Request language resolution

For every HTTP request, the backend resolves language in this order:

1. Authenticated user's saved `PreferredLanguage`
2. Query string `?lang=ar` or `?lang=en`
3. Header `X-App-Language`
4. Header `Accept-Language`
5. Fallback to English

This means:

- authenticated users automatically get their saved backend language
- public or unauthenticated endpoints can still be localized through headers

Example:

```http
GET /api/doctor/profile/12/public
Accept-Language: ar
```

In that case, backend-generated user-facing response text can still return in Arabic even without login.

---

## 2.4 Request culture and scoped language context

The backend now sets a scoped per-request language context.

That context is used for:

- localized response text
- localized exception handling
- culture-aware formatting
- backend-generated strings that depend on the current request language

The scope is reset safely after the request completes.

This reduces the risk of language leakage between requests.

---

## 2.5 Response localization middleware

The backend now includes a JSON response localization middleware.

Its responsibility:

- inspect JSON responses
- detect user-facing fields such as:
  - `message`
  - `error`
  - `title`
  - `details`
  - `errors`
- translate those values to the resolved request language when a known translation exists

It also handles:

- plain-text responses returned directly from controllers
- model validation payloads generated by ASP.NET Core

This allows the existing codebase to gain a lot of localization value without rewriting every controller manually first.

Important result:

- if an older endpoint returns `BadRequest("TargetEntity and TargetId are required")`, that response can still be localized centrally
- if a DTO validation attribute returns `Email is required`, that validation response can still be localized centrally

---

## 2.6 Global exception localization

The global exception middleware now localizes standard user-facing exception messages such as:

- authentication required
- validation failed
- database error
- external service failure
- timeout
- concurrency/update conflicts
- unexpected error fallback

So backend failure responses now participate in localization too.

## 2.8 Localized notifications

Notifications are now localized by recipient language.

This means the backend:

1. determines the target user
2. reads that user's preferred language
3. localizes the notification title/body for that language
4. stores the localized notification
5. pushes the localized notification

This matters because notifications may be triggered by:

- booking
- payments
- review actions
- profile completion
- admin moderation
- account status changes
- reminders
- support/ticket flows

Different users can receive notifications in different languages at the same time.

## 2.9 Localized emails

Emails are now localized by recipient language.

The backend:

1. resolves the recipient language from the user account
2. chooses a localized subject
3. builds a localized email template
4. applies correct direction:
   - English: `ltr`

5. formats embedded date/time text in the correct language

Localized email categories currently include:

- OTP email
- password reset email
- welcome email
- email verification email

- account blocked email

## 3. What Happens When a User Switches Language

## 3.1 Switching to Arabic

Flow:

1. Frontend sends:

```http
PUT /api/settings/language
Authorization: Bearer <token>
Content-Type: application/json

{
  "language": "ar"
}
```

2. Backend saves `PreferredLanguage = "ar"`
3. Future authenticated backend requests for that user resolve to Arabic
4. Backend messages and errors return in Arabic where registered
5. Notifications for that user are stored and pushed in Arabic
6. Emails sent to that user are generated in Arabic
7. Backend-generated formatted strings use Arabic-oriented formatting

## 3.2 Switching back to English

Flow:

1. Frontend sends:

```http
PUT /api/settings/language
Authorization: Bearer <token>
Content-Type: application/json

{
  "language": "en"
}
```

2. Backend saves `PreferredLanguage = "en"`
3. Future backend-generated user-facing text for that user returns in English

## 4. Important Clarification: Interface Language vs User Content

These are different things.

## 4.1 Interface or system language

This includes:

- buttons
- labels
- menu items
- tabs
- headings
- validation messages
- backend success and error messages
- notification titles and bodies
- email templates
- dashboard month labels

This is what should switch cleanly between Arabic and English.

## 4.2 User-generated content

This includes:

- ticket message text
- review comment text
- doctor note text
- patient note text
- manually written descriptions

This does not automatically change language.

If a user wrote English text before switching to Arabic, that content remains English unless you build a separate translation feature.

Localization and content translation are not the same problem.

## 5. How the Backend Works Now

## 5.1 Core request flow

For each HTTP request:

1. backend resolves the active language
2. backend opens a scoped language/culture context
3. controller/service logic executes
4. exception messages are localized when needed
5. JSON `message` / `error` fields are localized when possible
6. response returns with:
   - localized user-facing text
   - `Content-Language`

---

## 5.2 Notification flow

For each notification:

1. service decides to notify a user
2. backend resolves recipient preferred language
3. backend localizes title/body for that recipient
4. backend stores the localized notification
5. backend broadcasts and pushes the localized notification

---

## 5.3 Email flow

For each email:

1. service decides to send email
2. backend resolves recipient language
3. backend selects localized subject
4. backend builds localized HTML template
5. backend applies proper direction and formatting
6. backend sends the email

Frontend should not hardcode backend business-rule text.

- booking/payment errors

- moderation actions
- account status changes

## 8.10 Font system for Arabic and English

Fonts are a frontend responsibility.

The backend does not decide which font is used, but a professional bilingual app must use a deliberate font system.

### Why the font matters

Arabic and English do not behave the same way:

- Arabic glyphs connect and need proper shaping
- Arabic often needs more breathing room vertically
- English frequently looks best in a different UI font than Arabic
- weak font choices make Arabic look cramped even if translation is correct

So typography is part of localization quality.

### Recommended practical font pair

Recommended pair:

- English UI font: `Inter`
- Arabic UI font: `Cairo`

Good Arabic alternatives:

- `Tajawal`
- `Noto Sans Arabic`

Why `Inter` + `Cairo` is a strong combination:

- `Inter` is clean and excellent for dashboards, forms, and dense interfaces
- `Cairo` is modern and highly readable for Arabic UI
- both work well in healthcare/product/admin style interfaces

### How the frontend should apply fonts

Recommended rule:

1. If locale is English:
   - primary font = `Inter`
2. If locale is Arabic:
   - primary font = `Cairo`

Example font stacks:

- English:
  - `Inter, Segoe UI, Arial, sans-serif`
- Arabic:
  - `Cairo, Tajawal, Noto Sans Arabic, Segoe UI, sans-serif`

### Font fallback

Always define fallback fonts.

Why:

- if the primary font fails to load
- if some glyphs are missing
- if rendering differs by platform

the UI still stays readable and stable.

### Font weights

Recommended weights:

- body text: `400`
- labels: `500`
- buttons and section labels: `600`
- major headings: `700`

For Arabic:

- avoid very thin weights
- avoid excessive bold usage
- test line height carefully

### Arabic line-height guidance

Arabic often needs a slightly larger line height than English.

Practical rule:

- English body line-height:
  - `1.4` to `1.6`
- Arabic body line-height:
  - `1.6` to `1.8`

This improves readability and helps prevent clipping.

### Number rendering

Frontend must decide whether Arabic locale uses:

- Western numerals: `1 2 3`
- Arabic-Indic numerals: `١ ٢ ٣`

Pick one product rule and keep it consistent in:

- forms
- tables
- reports
- dashboard cards
- notification lists

If the backend returns a fully formatted display value, render it as returned.

### Font loading strategy

Frontend should:

1. preload the main UI fonts if possible
2. avoid visible layout jumps on language switch
3. switch font family and direction together with locale

Best behavior:

1. locale changes
2. typography theme changes
3. direction changes
4. app rebuilds once with the correct font and direction

### What can go wrong if fonts are handled badly

- Arabic looks too small
- Arabic text gets clipped vertically
- buttons overflow after switching language
- dashboard tables become harder to read
- punctuation and digits feel inconsistent
- mixed Arabic/English text looks visually broken

### Frontend font checklist

The frontend team should verify:

1. English screens use the English font consistently
2. Arabic screens use the Arabic font consistently
3. headings do not overflow after switching language
4. buttons do not clip Arabic text
5. forms remain readable in both languages
6. tables remain aligned in both languages
7. notification center text looks good in both languages
8. language switch updates font and direction together

1. User logs in
2. Frontend receives token
3. Frontend calls `GET /api/settings/language`

5. Frontend rebuilds the app using that locale

1. User changes language in settings
2. Frontend updates locale immediately
3. Frontend calls `PUT /api/settings/language`
4. Backend saves preference
5. Future backend messages, notifications, and emails use the new language

1. Frontend sends:
   - `Accept-Language: ar`

3. Backend returns localized backend-generated user-facing text where available
